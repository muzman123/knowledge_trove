> 4. **Common failure modes** — (a) jumping straight to code before clarifying the problem/examples; (b) never stating time/space complexity or discussing trade-offs before coding; (c) coding in silence instead of narrating thought process — interviewers read silence as poor communication, not focus. [DEV Community — Interviewer mistakes](https://dev.to/farhanaxmustafa/mistakes-ive-seen-as-a-technical-interviewer-1gdm), [DesignGurus — Common mistakes](https://www.designgurus.io/answers/detail/what-are-the-most-common-mistakes-to-avoid-in-coding-interviews)
> 5. **Naive recursive Fibonacci** — Confirmed: the simple recurrence T(n)=T(n-1)+T(n-2)+O(1) gives an easy upper bound of O(2ⁿ), but the *tight* bound, solving the recurrence exactly, is Θ(φⁿ) where φ = (1+√5)/2 ≈ 1.618 (the golden ratio) — so it's correct to say "O(2ⁿ) is a safe but loose upper bound; the real growth rate is ~1.618ⁿ." [GeeksforGeeks — Time complexity of recursive Fibonacci](https://www.geeksforgeeks.org/dsa/time-complexity-recursive-fibonacci-program/)
> 6. **CAP theorem** — A distributed system can't simultaneously guarantee Consistency (every read gets the latest write, everywhere), Availability (every request gets *a* response), and Partition tolerance (keeps working despite dropped/delayed messages between nodes) all at once. Since real networks *will* partition eventually, the practical, accurate framing is: partition tolerance is basically mandatory, so the actual trade-off you make **during a partition** is Consistency vs. Availability — return possibly-stale data (AP) or refuse to answer until synced (CP). [freeCodeCamp — CAP Theorem](https://www.freecodecamp.org/news/understanding-the-cap-theorem-consistency-availability-and-partition-tolerance-in-system-design/)
> 7. **Consistent hashing** — Confirmed one-sentence version: with K total keys spread over N nodes placed on a hash ring, adding or removing a single node remaps only about K/N keys (the ones between it and its ring-neighbor), versus naive mod-N hashing which can remap nearly all keys (e.g., ~80% with 5 nodes, ~99% with 100 nodes) on a single node change. [DesignGurus — Consistent Hashing / Dynamo](https://designgurus.substack.com/p/consistent-hashing-is-hard-until)
